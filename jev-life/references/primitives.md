# 三件套速查：Choice / Noul / Score

完整文档：https://docs.typesafe.ai/primitives.md

## Choice — 选一个

**何时用**：候选集合明确，需要 Jev 挑出最合适的那一个。

**构造要点**：

- `criteria` 是 map，key 是 option_id（用户/代码侧用），value 是该 option 的描述
- option 描述要写出**这个 option 代表什么**，不是描述它对应的事实
- 提供一个 `none` 或「不适用」option，让 Jev 在没有合适选项时能表达出来

**反模式**：

- 把 option 写成动词 + 同义词（"do A" / "perform A"）—— Jev 无法区分
- 选项超过 6 个且彼此重叠——概率会分散到无意义
- 选项互斥但描述里又有重叠场景——给 Jev 矛盾信号

## Noul — yes 还是 no

**何时用**：判断一个条件是否成立。注意 Noul **不是「程度」**，靠近 0.5 表示 yes/no 概率相近，**不是**中等强度。

**构造要点**：

- `instructions` 写成可二选一的问题，避免「在多大程度上」这种程度化措辞
- `criteria.true` 和 `criteria.false` 各自说明 yes/no 接近 1/0 时意味着什么
- 一个语义独立的问题用一个 Noul；如果几条独立 yes/no 都需要，问**多个** Noul（每个一个 question_id），不要塞进同一个

**反模式**：

- 用 Noul 表达「稍微可能」—— 这是 Score 的工作
- 在 `instructions` 里堆条件导致 yes/no 边界模糊

## Score — 有序等级

**何时用**：判断沿某个可描述维度处于哪一档。

**构造要点**：

- `criteria` 是**有序**数组（从低到高或从高到低，**固定方向**）
- 2–10 档；一般 3–5 档最易读
- 每档描述**具体场景**，不是抽象形容词
- 档之间**互相独立且可识别**——不要让相邻档只有细微差别

**反模式**：

- 用「一般/中等/良好」这种抽象形容词—— Jev 没有锚点
- 档数太多（>7）导致每档样本太少，概率分散
- 方向不一致（开头低、中间高、结尾低）——Jev 需要稳定的方向

## 三件套在同一请求里的角色分工

在 jev-life 里，**三个 question 共享同一份 `state`**，但扮演不同角色：

| Primitive | 在三元语里的角色 |
| --- | --- |
| Choice | 从候选策略中挑出**最适合当前情境的那一个** |
| Noul | 评估**选中的策略**有多大可能成功 |
| Score | 给选中的策略在「整体质量」维度上打分 |

不要让三个 question 问**完全独立**的事——它们应共同刻画对同一组候选的判断。如果发现三件套之间毫无关联，说明场景拆错了，回到 Step 2 重新框。
